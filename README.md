본 데모 프로젝트는 실험 D에서 검증한 Opinion Units 기반의 구조화된 속성 추출과 계층적 군집화를 활용한 속성 정규화를 **지속적인 데이터 유입과 카탈로그 변화에 대응할 수 있는 운영 시스템으로 전환**하는 것을 목표로 합니다.

* 시스템 아키텍쳐 구성
* 시스템 중점 설계 정책
	1. 독립적이고 재현 가능한 데이터 파이프라인
	2. 카탈로그 진화 시스템
	3. 데이터 및 카탈로그 품질 관리
* 데모 페이지 설명

## 시스템 아키텍쳐 구성

<img src="https://raw.githubusercontent.com/Experience-Driven-Product-Catalog/review-catalog-platform/refs/heads/main/assets/LEVIT%20%EC%8B%A4%ED%97%98-3.png" width="100%" />

- React와 FastAPI를 통해 전체 시스템을 구성하였으며 Airflow를 통해 데이터 처리 및 카탈로그를 관리합니다.
- 사용자 요청 및 결과 조회와 같은 운영 영역은 FastAPI가, 데이터 처리 및 카탈로그 관리 영역은 Airflow가 담당하도록 책임을 분리하였습니다.
- 운영 정보와 Airflow Metadata는 PostgreSQL에 저장하고, 리뷰 및 카탈로그 데이터는 DuckDB에 저장합니다.
- AWS 단일 EC2 인스턴스에 Docker 기반으로 배포하고, GitHub Actions를 이용해 CI/CD를 구성하였습니다.

카탈로그 운영을 위해 두 개의 Airflow DAG를 분리하여 운영합니다.

* **`Catalog_ingestion`**
	* 신규 리뷰에서 Opinion Units를 추출하고 속성을 정규화하여 카탈로그 데이터를 생성합니다.
	* 매일 00시에 자동 실행되며, 사용자가 Frontend에서 명시적으로 요청한 경우에도 실행할 수 있습니다.
	* 신규 속성은 현재 활성화된 카탈로그의 Mapping Table과 군집 정보를 이용해 기존 Canonical Attribute에 우선 매핑합니다.
	* 기존 속성에 안정적으로 연결하기 어려운 표현은 즉시 카탈로그 구조를 변경하지 않고 **신규 속성 후보**로 별도 저장합니다.
* **`Catalog_reclustering`**
	* 운영 과정에서 축적된 신규 속성 후보를 포함해 전체 속성 군집과 Canonical Mapping을 재구성합니다.
	* 데이터 품질과 신규 후보의 규모를 확인한 운영자가 명시적으로 실행하도록 설계하였습니다.
	* 재구축 결과는 기존 카탈로그를 직접 수정하지 않고 **새로운 Catalog Version**으로 생성합니다.
	* 속성 데이터뿐 아니라 정적 분석 보고서와 동적 의사결정 제안서 역시 어떤 카탈로그 버전을 기준으로 생성되었는지 추적할 수 있도록 구성하였습니다.

## 시스템 중점 설계 정책

지속 가능한 운영 시스템으로 전환하기 위해 다음 세 가지 요소에 중점을 두었습니다.

### 1. 독립적이고 재현 가능한 데이터 파이프라인

사용자 요청과 결과 조회와 같은 **온라인 서비스는 FastAPI,** 속성 추출 및 정규화, 그리고 저장 및 카탈로그 구축과 같은 **데이터 처리는 Airflow**가 담당하도록 책임을 분리하였습니다.

이를 통해 데이터 처리 과정에서 장애가 발생하더라도 현재 사용자에게 제공 중인 서비스와 활성화된 카탈로그에는 영향을 주지 않도록 하였습니다.

* **장애 범위 분리**: FastAPI의 온라인 조회 경로와 Airflow의 배치 처리 경로를 분리하여 데이터 처리 장애가 서비스 조회에 전파되지 않도록 하였습니다.
* **Task 단위 재시도**: 데이터 처리 과정을 여러 Airflow Task로 분리하여 전체 파이프라인을 중단하거나 다시 실행하지 않고 실패한 단계부터 재시도할 수 있도록 하였습니다.
* **멱등성**: 리뷰마다 ID를 부여해 이미 처리한 동일 리뷰가 중복으로 카탈로그에 반영되지 않도록 하였습니다.
* **재현성**: 실행별로 입력 데이터와 사용된 모델, 프롬프트, 카탈로그 버전, 등을 기록하여 결과가 생성된 조건을 추적할 수 있도록 하였습니다.

LLM은 동일한 입력에서도 항상 동일한 출력을 보장하기 어렵기 때문에, 결과 자체의 완전한 재현성보다는 **어떤 입력과 설정을 통해 결과가 생성되었는지를 복원하고 비교할 수 있는 프로세스 재현성을 확보**에 중점을 두었습니다.

### 2. 카탈로그 진화 시스템

운영 과정에서 지속적으로 유입되는 데이터를 바탕으로 카탈로그를 재구성함으로써 새로운 리뷰 표현을 반영하고, 시간의 흐름에 따라 지속적으로 발전할 수 있는 카탈로그 시스템을 구축하고자 하였습니다.

- **재군집화**
	- 신규 속성 후보가 일정량 축적되거나 운영자가 카탈로그 갱신이 필요하다고 판단하면 `Catalog_reclustering` Airflow DAG를 명시적으로 실행하여 카탈로그 재구축을 수행합니다.
	- 재군집화가 진행되는 동안에도 신규 리뷰 처리를 중단하지 않습니다. 해당 시점에 유입되는 데이터는 기존 활성 카탈로그를 기준으로 계속 처리하고, 이후 새로운 카탈로그 재구축 과정에 반영할 수 있도록 하였습니다.
- **버전 관리 및 장애 대응**
	- 재군집화 결과는 현재 카탈로그를 직접 덮어쓰지 않고 새로운 버전으로 생성합니다.
	- 기존 데이터를 덮어쓰지 않고 버전 단위로 관리함으로써 과거 카탈로그와 신규 카탈로그를 비교하고, 속성 및 Mapping 변경 이력을 추적하고 분석할 수 있도록 하였습니다.
	- 기존 카탈로그와 신규 카탈로그의 결과를 비교하고 Canonical Attribute 및 Mapping의 변경 이력을 추적할 수 있도록 하였습니다.
	- 신규 버전에서 문제가 발견될 경우 이전 버전으로 복구할 수 있도록 구성하였습니다.

### 3. 데이터 및 카탈로그 품질 관리

Airflow DAG가 정상적으로 종료되었다는 사실만으로 생성된 데이터의 품질이 보장되지는 않습니다. 따라서 시스템 운영 상태와 카탈로그 데이터 품질을 구분하여 관리하도록 설계하였습니다.

- **기본 데이터 검증**
	- "`excerpt`가 실제 리뷰 원문에 존재하는지"와 같이 반복적으로 확인할 수 있는 명확한 오류는 데이터가 카탈로그에 반영되기 전에 Airflow Task 단계에서 검증하여 오류가 이후 단계로 전파되는 것을 방지합니다.
- **카탈로그 상태 관찰**
	- 기존 Canonical Attribute에 대한 매핑 비율, 자주 등장하는 속성과 속성 분포 등을 통해 카탈로그 상태를 관찰할 수 있습니다.
	- 정적 카탈로그 분석 보고서와 동적 의사결정 제안서를 Frontend에서 확인할 수 있도록 하여, 생성된 카탈로그가 실제 분석과 의사결정에 어떻게 활용되는지도 함께 시연합니다.
- **카탈로그 오염 방지**
	- 기존 카탈로그에 안정적으로 매핑하기 어려운 표현을 곧바로 신규 Canonical Attribute로 확정하지 않고 후보로 축적함으로써, 일시적인 표현이나 LLM 출력의 변동이 운영 중인 카탈로그를 불필요하게 변경하는 것을 방지하였습니다.
	- 축적된 신규 후보는 재군집화 과정에서 운영자가 검토할 수 있습니다.

### 정리

본 데모에서는 단순히 LLM을 이용해 리뷰 속성을 추출하는 것을 넘어, 검증된 추출 및 정규화 방식을 실제로 지속 운영하기 위해 어떤 구조가 필요한지에 초점을 두었습니다.

이를 위해

1. 온라인 서비스와 데이터 파이프라인을 분리하여 장애와 재처리를 관리하고,
2. 버전 기반 재군집화를 통해 카탈로그를 중단 없이 발전시키며,
3. 데이터 검증과 품질 관찰을 통해 신규 데이터가 기존 카탈로그를 무분별하게 변경하지 않도록 통제하였습니다.

최종적으로 일회성 속성 추출 실험을 지속적인 데이터 유입과 카탈로그 변화에 대응할 수 있는 운영형 카탈로그 시스템으로 전환하고자 하였습니다.

* 동일한 분석 API를 활용해 개별 상품뿐 아니라 **전체 상품에 대한 통합 분석**도 수행할 수 있습니다.
* 속성 감성 행렬 위에서 가장 최근에 추가된 리뷰와 해당 리뷰에서 추출·정규화된 속성을 확인할 수 있습니다.

사용자가 직접 리뷰를 입력하면 실험 D의 방식에 따라 Opinion Units를 추출하고 기존 카탈로그와 연결하여 분석합니다.

* 추출된 Opinion Units와 함께 **기존 리뷰의 속성 분포와의 비교, 유사한 리뷰 분석, 상품 분석 및 대안 상품 추천**을 포함한 동적 의사결정 제안서를 제공합니다.
* 동적 의사결정 제안서 역시 **카탈로그 데이터를 활용한 규칙 기반 방식**으로 생성됩니다.
* 입력한 리뷰 수에 따라 프런트에서 계산한 예상 타이머와 파이프라인 진행 상태를 함께 확인할 수 있습니다.
* 배송 상태처럼 상품과 관련되지 않아 속성이 추출되지 않은 리뷰는 빈 표 대신 제외 이유를 표시합니다.

이를 통해 새로운 리뷰가 입력되었을 때 카탈로그 데이터를 활용하여 **상품 분석과 구매 의사결정에 필요한 정보를 동적으로 제공하는 과정**을 확인하는 것이 데모 페이지의 목적입니다.

## 실행 및 검증

### Docker 실행

```bash
cp .env.example .env
docker compose build
docker compose up -d
docker compose ps
```

위 명령어를 통해 Docker를 실행하여 서비스를 구성할 수 있습니다. 이때 속성 추출을 위한 `codex_cli` 인증이 필요함으로 docker의 scheduler 컨테이너에서 다음 방벙을 통해 최초 인증이 필요합니다. 인증 파일은 모든 Airflow 서비스가 공유하는 `codex_auth` named volume의 `/home/airflow/.codex`에 저장되기에 일반적으로 image 재빌드 후에도 유지됩니다.

```bash
docker compose exec airflow-scheduler codex login --device-auth
docker compose exec airflow-scheduler codex login status
```

실행된 서비스는 다음 주소에서 확인할 수 있습니다.

- UI: `http://localhost:3000`
- FastAPI/OpenAPI: `http://localhost:8000/docs`
- Airflow: `http://localhost:8080`

```bash
cd backend
uv sync --extra embedding --extra reclustering --dev
uv run ruff check src tests
uv run pytest -q

cd ../frontend
npm run build

cd ..
docker compose config --quiet
```
